# Content trail

The capture’s header now shows its source app mark, a directional arrow, and up to three destination marks. Extra destinations collapse to +N. Select the trail to see app names, event times, and whether each paste was confirmed or manually recorded. The adjacent + records a destination through direct app choices or a custom product name.

The same component appears on task cards, capture/task details, and the robot’s last saved item. Conversion keeps the same record and trail. Recurrence keeps the source but starts with an empty paste history. Multiple pastes into one app remain individual history events while sharing one destination mark on the card.

## Truth and data boundaries

Build 53 does not observe later cross-application pastes. This change designs and implements the local usage ledger; it does not add native system monitoring. Existing records receive no invented destinations. Copying, opening a product, or selecting a source app must never be treated as proof that a paste succeeded.

- `sourceProduct`, if explicitly supplied by an adapter, takes precedence over `sourceApplicationBundleIdentifier`, `sourceApplicationName`, then legacy `source`.
- `pasteHistory` is optional and additive. Entries contain `id`, `app`, ISO `at`, and `kind` (`manual` or `confirmed`). Optional `label` names an unknown app; optional `context` carries a supplied document/channel name. Neither is inferred from captured text.
- Browser interactions create only `manual` entries, visibly labeled “Recorded by you” in history. They do not activate other apps or paste content.
- `confirmed` is a rendering contract for a future trusted native adapter. Use it only for an actual successful, explicitly supported paste operation, never a clipboard write or a frontmost-app guess. No confirmed receipts are generated by this prototype.
- Unknown origins remain “Unknown source”; empty usage shows “No pastes.” Unknown products receive a neutral app symbol and their actual supplied name. A copied link’s target is not assumed to be the source website.
- No automatic web favicon requests: captured content and app identity stay local. Installed app icons should resolve through the existing native `CaptureApplicationIconCache`. Website product identities require reliable source metadata and a verified cached mark.

## Assets and implementation

`provenance.js` and `provenance.css` are included by `build.py` in all 19 screens. Real Mail, Notes, Finder, Safari, Chrome, and Slack icons were extracted from their local application bundles. Original ICNS files are preserved byte-for-byte beside 96px PNG previews in `assets/app-icons/`; `provenance.json` records the exact source and bundle IDs. DaBin uses its existing original robot asset. Brand marks are used only to identify source/destination products.

## Verification

279 behavior, markup, route, asset, and contrast checks pass. New checks cover missing/unknown origins, bundle resolution, repeated destination history, escaping, manual versus confirmed attribution, failed-storage rollback, removal, conversion and undo, and recurrence isolation. These are not rendered browser or native integration checks; those remain pending as documented in QA_REPORT.md.
